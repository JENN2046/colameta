## Data Structure Changes

### 1. P1 v2 schema boundary

The destructive replacement of caller-authored local-validation assertions is
an explicit schema transition:

```text
colameta.p1_release_evidence.v2
colameta.p1_release_evidence_preview.v2
colameta.p1_release_evidence_receipt.v2
```

The v2 intake advertises and accepts only the new `validation_run` reference
shape. Every newly created P1 preview is v2. A legacy v1 preview is invalid
after the upgrade and must fail apply with a bounded version error; it may be
discarded but never converted or applied.

Receipt status uses a strict two-version reader:

- v2 receipts are eligible for normal re-verification;
- v1 receipts remain read-only historical records;
- a v1 receipt is never rewritten, backfilled, migrated, or
  `verified_current`;
- an integrity-valid v1 receipt may report at most `verified_stale` with
  `evidence_complete=false` and a legacy-provenance reason;
- recovery requires a fresh manifest-bound validation run, a new v2 preview,
  and a new v2 receipt.

No mixed v1/v2 object is accepted. Preview/apply must require exact schema keys
for the selected version.

### 2. Terminal validation result

Every newly persisted terminal result (`status` equal to `passed` or `failed`)
must use:

```json
{
  "schema_version": "colameta.validation_run_result.v1",
  "run_id": "validation_run_...",
  "preview_id": "...",
  "action": "run",
  "status": "passed",
  "passed": true,
  "scope": "manifest_bound",
  "target_files": [],
  "strategy": "manifest_acceptance",
  "validation_groups": [],
  "command_summary": [],
  "command_count": 0,
  "command_results": [],
  "failed_command_indexes": [],
  "failed_command_index": null,
  "output_summary": {},
  "started_at": "...",
  "completed_at": "...",
  "duration_seconds": 0.0,
  "manifest_validation": {},
  "validation_result_sha256": "<64 lowercase hex>"
}
```

`manifest_validation` remains optional for ordinary non-manifest validation
runs, but it is mandatory for P1 eligibility. The terminal top-level schema is
closed: missing or unknown persisted fields fail verification. Normal and
exceptional terminal paths must emit the same top-level field set.

A non-terminal `running` record is explicitly not P1-eligible and must not
contain `validation_result_sha256`. The closed running schema requires the
digest field to be absent; a running record that contains it is schema-invalid.
A valid running record without a digest remains readable as non-terminal and is
not legacy corruption or an integrity failure.

Status/read uses the following exact response-only integrity classifications;
they are never persisted inside the result and therefore are not included in
`validation_result_sha256`:

```text
non_terminal
verified
unverified_legacy
integrity_failure
```

The classifications are disjoint:

- a schema-valid running/non-terminal record with no digest is `non_terminal`;
- a current-schema terminal result whose digest verifies is `verified`;
- a legacy terminal result with no digest is `unverified_legacy` and fails
  closed without backfill or migration;
- a terminal result with a present digest that differs from the freshly
  recomputed canonical digest is `integrity_failure`.

Absence of a digest on a terminal record must never be collapsed into digest
mismatch, and digest mismatch must never be reported as `unverified_legacy`.

### 3. P1 validation reference input

Replace caller-supplied per-command `"passed"` assertions with an exact
reference:

```json
{
  "full_local_validation": {
    "validation_run": {
      "run_id": "validation_run_...",
      "validation_result_sha256": "<64 lowercase hex>",
      "contract_sha256": "<64 lowercase hex>",
      "manifest_sha256": "<64 lowercase hex>"
    }
  }
}
```

The server derives `observed_at` from the verified result `completed_at` and
derives `candidate_head` from the verified existing manifest validation
contract. Neither value is accepted as a caller assertion for this evidence
group.

The normalized P1 preview/receipt observation records the four references above
plus the derived `observed_at`, `candidate_head`, and a source kind such as
`server_verified_validation_run`. The other four P1 evidence groups remain
explicitly `operator_attested`.

The preview and receipt use their explicit v2 schema versions for this shape.
The existing `receipt_digest` algorithm remains unchanged and therefore covers
the embedded validation reference without adding another receipt protocol.

## One Internal P1 Validation Result Verifier

Implement one internal verifier in the existing validation/P1 modules and call
that same verifier from P1 `preview`, `apply`, and `status`/`inspect`. Do not
implement three similar verification paths.

The verifier accepts a validated `run_id`, candidate/freshness context, and
expected comparison hashes. It must not accept a result filename, directory,
absolute path, relative path, file URI, or caller-supplied result object. Only
the validation-run manager may map `run_id` to the bounded internal result
location and read the persisted result.

For every call, the verifier must establish these internal facts in fail-closed
order:

1. the bounded result file selected internally from `run_id` exists and is a
   readable regular file inside the validation-run result store;
2. the result schema is valid and its state is terminal;
3. terminal `status=passed` and `passed=true`;
4. the persisted `validation_result_sha256` equals a fresh canonical digest of
   the stored terminal result;
5. the embedded existing manifest validation contract is structurally valid;
6. its `contract_sha256` equals a fresh canonical digest of the existing
   contract payload;
7. its `command_specs_sha256` equals a fresh canonical digest of the embedded
   fixed command specs;
8. the contract candidate HEAD, P1 candidate, and required current HEAD
   relationship match the operation phase;
9. every required P1 command family is present exactly as allowed by the
   existing fixed argv contract, every expected command result is present in
   order, and all required results passed;
10. `completed_at` is valid and within the P1 freshness window.

Only after those facts are established may the verifier compare the
caller/preview/receipt expected `validation_result_sha256`,
`contract_sha256`, and `manifest_sha256` values with the internally verified
facts. All caller-provided SHA values are expected comparison values only. The
sole fact source is the persisted validation result located internally through
`run_id`.

The source of expected values is phase-specific:

| P1 phase | Expected comparison values |
| --- | --- |
| `preview` | Closed v2 intake reference. |
| `apply` | The already-digest-bound v2 P1 preview. |
| `status` / `inspect` | The already-digest-bound v2 receipt; never fresh caller hashes. |

The verifier returns a normalized, non-path-bearing verified result projection
for the P1 evaluator. It does not run validation, modify the result, or grant
release/stable authority.

## Canonical Validation Result Digest

Let `R` be the exact closed, persisted terminal result mapping after
`schema_version` and all terminal fields have been populated, but before
`validation_result_sha256` is inserted.

Reject non-JSON values and non-finite numbers. Compute:

```python
canonical_bytes = json.dumps(
    R,
    ensure_ascii=False,
    sort_keys=True,
    separators=(",", ":"),
    allow_nan=False,
).encode("utf-8")
validation_result_sha256 = hashlib.sha256(canonical_bytes).hexdigest()
```

Use the existing canonical JSON SHA-256 helper semantics from
`runner/review_manifest_validation.py`; import and reuse them rather than
creating a second canonicalization convention. The valid-value output must
remain byte-for-byte compatible with the existing manifest-contract
canonicalizer.

The digest covers all persisted terminal fields, including redacted/truncated
command output, timings, ordered command results, and the complete existing
`manifest_validation` contract. It excludes only its own
`validation_result_sha256` field. Response-only projections such as `ok`,
status-call `action`, `project_name`, operation context, workflow metadata, or
`run_file` are not persisted terminal fields and are not part of the digest.

Object-key order is insignificant. Array order, value changes, field removal,
and field addition are significant. Reordering JSON object keys alone must
continue to verify; changing semantic content must not.

## SHA-256 Trust Boundary And Documentation Language

Both allowed P1-E documents must use the exact concept `canonical integrity
binding` when describing `validation_result_sha256`, contract hashes, and the
receipt chain. They must state all of the following:

- SHA-256 is not a digital signature;
- SHA-256 is not remote attestation;
- SHA-256 does not prove executor or operator identity;
- an unkeyed digest cannot resist a malicious or privileged local writer that
  can rewrite both the persisted result and its digest;
- `server_verified_validation_run` means verified inside the bounded local
  server trust model, not cryptographically authenticated execution provenance;
- v1.19 does not add HMAC, digital signatures, external attestation, or a new
  trust authority.

Do not describe the result as tamper-proof, unforgeable, signed, remotely
attested, or immutable. The binding detects semantic divergence relative to
retained expected hashes and preview/receipt bindings within the stated local
trust boundary.

## Required Verification Behavior

1. Finalization constructs the closed terminal mapping in memory, computes and
   inserts its canonical digest before persistence, then performs one atomic
   replacement through the existing result path. It must never expose an
   unhashed terminal record. Both success and failure/exception terminal paths
   produce the v1 result schema and digest.
2. `manage_validation_run status`, and any internal result-read API used by P1,
   must parse the raw persisted record, validate the applicable closed
   running/terminal schema, recompute a terminal digest, and compare it in
   constant time before adding response projections. A valid running record
   must have no digest and returns `integrity_classification=non_terminal`.
3. A terminal legacy result with no digest fails closed with a bounded error
   and the exact response classification
   `integrity_classification=unverified_legacy`. It must never be silently
   upgraded, backfilled, treated as digest mismatch, or accepted by P1.
4. A present terminal digest that differs from a fresh canonical digest fails
   closed with the exact response classification
   `integrity_classification=integrity_failure`. Malformed results, unknown
   terminal schemas, or invalid manifest validation contracts also fail closed,
   but must not be mislabeled `unverified_legacy`.
5. A schema-valid `running` result without a digest remains readable as
   non-terminal but cannot satisfy P1. A running record containing a digest
   fails its closed schema. A `failed` terminal result remains
   integrity-verifiable but cannot satisfy P1.
6. P1 preview calls the one internal verifier with `run_id`; the verifier
   internally resolves and reads the result, performs the full result/contract/
   command-spec/candidate/coverage/freshness verification, and only then compares
   v2 intake expected hashes.
7. P1 accepts only `status=passed`, `passed=true`, zero failed command indexes,
   and complete ordered command results for the existing fixed command specs.
8. Retain the existing five P1 local-validation requirements—pytest,
   self-hosting smoke, compileall, Ruff, and `git diff --check`—but derive their
   completion from the verified contract command specs and result entries.
   Caller-provided `"passed"` strings are no longer evidence.
9. P1 preview requires the contract candidate, requested candidate, and current
   HEAD to match. P1 apply calls the same internal verifier again and repeats
   every result, contract, command-spec, candidate, coverage, terminal-state,
   and freshness check instead of trusting the preview snapshot.
10. P1 apply compares all newly verified hashes with the values frozen in the
    v2 P1 preview. Any result rewrite after preview fails, even if the rewritten
    result carries a newly recomputed digest.
11. P1 status/inspect first validates the receipt digest, then uses the
    receipt-bound `run_id` and expected hashes to call the same internal verifier.
    It must not accept caller replacement hashes or paths.
12. If a receipt-referenced result is modified, malformed, moved, deleted, or
    unreadable, status returns `evidence_complete=false`, must not return
    `verified_current`, and the unchanged P1 gate remains blocked. A missing
    result uses `P1_VALIDATION_RESULT_NOT_FOUND`.
13. A later repository HEAD change makes an otherwise valid receipt
    `verified_stale`. It must not automatically create a `superseded` status.

Required stable P1 verifier errors include:

```text
P1_VALIDATION_RESULT_NOT_FOUND
P1_VALIDATION_RESULT_NOT_TERMINAL
P1_VALIDATION_RESULT_NOT_PASSED
P1_VALIDATION_RESULT_DIGEST_MISMATCH
P1_VALIDATION_CONTRACT_DIGEST_MISMATCH
P1_VALIDATION_COMMAND_SPECS_DIGEST_MISMATCH
P1_VALIDATION_MANIFEST_DIGEST_MISMATCH
P1_VALIDATION_CANDIDATE_MISMATCH
P1_VALIDATION_RESULT_STALE
P1_VALIDATION_COMMAND_COVERAGE_INCOMPLETE
P1_VALIDATION_RESULT_CHANGED_AFTER_PREVIEW
P1_LEGACY_VALIDATION_PROVENANCE_MISSING
P1_LEGACY_PREVIEW_NOT_APPLICABLE
```

Malformed result or contract structures may use an additional stable
schema-invalid code, but they must not collapse any of the required distinctions
above. Do not expose raw private-state paths or unredacted command output in
errors.

## Compatibility And Migration

- Existing review manifests and
  `colameta.review_manifest_validation_contract.v1` remain valid and unchanged.
- Existing `manifest_sha256`, context, subjects, fixed argv,
  `command_specs_sha256`, and `contract_sha256` are reused as the durable
  validation contract inside the result.
- New terminal results receive
  `colameta.validation_run_result.v1` and a digest.
- Existing terminal validation results without that digest remain historical
  but untrusted for P1. Status/read fails closed with
  `integrity_classification=unverified_legacy`; no synthetic digest is written.
- P1 intake, preview, and receipt writers move to their explicit v2 schemas.
- New preview generation emits only v2. Existing v1 previews fail apply and are
  never upgraded.
- Existing P1 receipt v1 files are never rewritten. A strict read-only v1 reader
  may validate their original receipt digest and report historical metadata, but
  the local validation check is blocked as legacy provenance and the receipt
  cannot be `verified_current`. Use `verified_stale`, not `superseded`, for an
  integrity-valid legacy receipt that lacks the new bridge.
- Recovery requires a fresh manifest-bound validation run followed by a fresh
  v2 P1 preview/apply and a new v2 receipt. There is no in-place migration.
- Short-lived `review_manifest_id` and validation `preview_id` remain auxiliary
  handles, not durable authority. The result and P1 receipt retain the existing
  manifest/contract hashes.

| Stored/caller artifact | Read/status behavior | Apply/current-evidence behavior |
